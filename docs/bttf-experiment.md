# BTTF(arXiv:2610.06790)两表 SQLite 方案: 在我们真实 FSDB 上的对照实验

> **状态**: 🧪 实验(dev 分支 `dev/bttf-waveform-db`),**未采纳为默认路径**。
> **装置**: `scripts/bench_bttf_sqlite.py`(纯 Python, 直接读我们自己的 `.fcol` 列缓存)。
> **一句话结论**: **它的"引擎"不适合我们(体积 11×、聚合查询慢 3~4 个数量级), 但它的"schema"值得抄**(每信号预计算统计让 top-N / 窗口活跃从"扫全表"变成 O(1))。

## 1. 论文说了什么

BTTF 把 `.fsdb`/VCD 归一化进 **SQLite 两张表**: `signal_metadata`(信号是谁)+ `signal_changes`(时间, 值),
外键关联;建库时做三种剪枝(砍时钟 / 丢零翻转 / 丢低于平均翻转率)+ 批量插入(`EXECUTEMANY`);
上面挂多 agent(text-to-SQL + 五标准审计)。报告 150 题 **95.33%** 执行准确率;
剪枝账: 1,420MB → 480MB(−66.2%)、查询 410.5ms → 125.2ms(3.28×)、保留 98.51% 功能翻转覆盖;
激进档 185MB / 41.6ms 但掉 35.77% 覆盖。

## 2. 我们怎么对照的(同一批行, 两份存储)

* **数据源**: 真波形(336MB / 17,956,098 信号)上已缓存的 **265 条变更列**(`WALFCOL2` 格式,
  直接按字节解析, 与 CLI 无关)——**19,528,003 行**变更记录, 我们这边落盘 **81.1 MB**(**4.15 B/行**)。
* **对照侧**: BTTF 的两表 schema + 它的两个索引(`(sig_id,time)`、`(time)`)+ `executemany` 分批插入;
  查询取 7 次中位数。变体: `full` / `active_above_avg`(论文的"低于均值剪枝")/ `drop_heavy`(丢重翻转 = 论文的"砍时钟"那一档)。
* **额外两条查询**: 同样的问题改吃 `signal_metadata`(`n_changes` + 首末时间), 用来区分"引擎慢"还是"schema 没设计好"。

## 3. 结果

| 变体 | 体积 | 行数 / 覆盖 | 建库 | value@t | 翻转计数 | **top-N 翻转** | **窗口内活跃** | rising 计数 | top-N(吃 metadata) | 窗口活跃(吃 metadata) |
|---|---|---|---|---|---|---|---|---|---|---|
| 我们的 `.col` | **81.1 MB** | 19.53M / 100% | —(写列时顺带) | —(读列 ~ms) | —(会话内 600 次计数 ≈ 0) | — | — | — | — | — |
| SQLite `full` | **916.7 MB** | 19.53M / 100% | **15.8s**(1.24M 行/s) | 0.008ms | 2.02ms | **499ms** | **2042ms** | **65.9ms** | **0.019ms** | **0.013ms** |
| SQLite `active_above_avg` | 897.8 MB | 19.20M / 98.3%行 · 55.5%信号 | 16.2s | 0.008ms | 2.08ms | 497ms | 1996ms | 65.3ms | 0.015ms | 0.011ms |
| SQLite `drop_heavy`(砍重翻转) | **17.9 MB** | 0.33M / **1.7%行** · 44.5%信号 | **0.24s** | 0.007ms | 0.007ms | 8.2ms | 24.6ms | 0.008ms | 0.015ms | 0.009ms |

**我们侧的同批查询**(单次 `--stdin` 会话, 暖 `.fcol`, wall 含加载):

| 会话 | 探针数 | 墙钟 | 峰值 RSS |
|---|---|---|---|
| 只加载(`(length (SIGNALS))`) | 1 | 9.31s | 6.34GB |
| 加载 + `(at sig t)` + `(count (changes sig))` | 2 | 8.33s | 6.34GB |
| 加载 + **600 个信号的翻转计数**(= top-N 的数据面) | 600 | 8.32s | 6.51GB |

> 600 次计数的边际成本**低于测量噪声**: 墙钟完全由加载主导(8.3~9.3s, 页缓存敏感)。

## 4. 裁决(逐条假设)

| 假设 | 结果 | 证据 |
|---|---|---|
| H1 关系库体积可接受 | **否** | 同一批行: 916.7MB vs 81.1MB = **11.3×**(47 B/行 vs 4.15 B/行) |
| H2 点查更快 | **平** | `value@t` 0.008ms vs 我们读列 ~ms 级(都够快) |
| H3 聚合查询(SQL 直查)更快 | **否** | `top-N` 499ms、`窗口活跃` **2042ms**、`rising` 65.9ms —— 而同一作业在我们路径上是"加载后≈0"(600 次计数低于噪声) |
| H3′ 换用**它的 metadata 表** | **是(关键发现)** | 同样两条查询改吃 `signal_metadata` → **0.019ms / 0.013ms**(快 **2.6 万倍 / 15 万倍**)。**赢在 schema, 不在引擎** |
| H4 批量插入是瓶颈 | **是但不重要** | 分批 `executemany` 下 15.8s 写完 19.5M 行(**1.24M 行/s**);写不是瓶颈,**查询形态**才是 |
| H5 剪枝(砍时钟)省得动 | **省, 但代价被我们低估** | 砍掉 147 个重翻转信号: 体积 −98%(17.9MB)、建库 66×、聚合回到 ms 级 —— 但它们占 **98.3% 的行**, 覆盖掉到 **1.7%** |

**两个口径差异必须写明**(否则会误读):
1. 论文的"98.51% 功能翻转覆盖"是**按非时钟口径**统计的;我们表里的 `覆盖率` 是**全部行(含时钟)**占比, 两者不可直接比。
2. 我们的"98.3% 行集中在 147 个信号"说明**这份波形的重尾比论文的 4.2GB/18,450 网更极端**(他们三个数量级更小), 所以"砍时钟"在我们这里的收益更大、**风险也更大**。

**不公之处(自我约束, 免得吹)**:
* SQLite **没有调参**(`page_size`/`cache_size`/`WITHOUT ROWID`/covering index/`ANALYZE`);认真调大概能好 2~3×, 但补不上 3~4 个数量级的差。
* 我们侧的数字是**整会话口径**(含 ~8-9s 加载 + NPI 许可), 不是单片查询的 A/B;`.col` 的大小对比是**格式级**的, 严格可比。
* `drop_heavy` 的"覆盖"是按行算的, 不代表"有用信息"占比 —— 时钟翻转在调试里确实信息量低, 这点论文说得对。

## 5. 采纳 / 不采纳

**采纳(全部是 schema 与工程, 不换引擎)**
1. **每信号统计侧车**(`n_changes` / `first` / `last` / 密度): 写列时顺手记, 让 top-N、窗口活跃、静默网发现变成 O(log n)。
   这正是让 SQLite 那两条查询从 499ms/2042ms 掉到 0.019ms/0.013ms 的东西 —— **与我们用什么存储无关**。
2. **按变更密度做分片装箱**: 我们的 depth8 反例("按信号数均衡 ≠ 按工作量均衡")由此有了现成的权重来源。
3. **列打包 + 会话级预取**(对应他们的批量插入思路): 一个 agent 会话要几十~几百个列时, 省掉逐文件开销。
4. **给 agent 的 schema 化接口**: 补齐 7 个指标算子的 `--help`/`(doc)`, 加 `wal-rust schema --json`。
   论文的对照实验(单 agent 会在 schema 上幻觉)说明这比模型能力更决定成功率。

**不采纳**
* SQLite 作为查询引擎(体积 11×、聚合慢 3~4 个数量级、且会丢掉索引空间/`INDEX`/`TS`/4-state 语义)。
* 剪枝当**默认**视图(动的是索引空间: 实测真波形 320,204 个时间点里单个时钟就贡献 130,590 次变化)。
  只做**显式探索视图**(`WAL_FSDB_VIEW=full|no-clock|active`)并在结果里声明覆盖率;默认永远 full。
* 多 agent 编排(他们的 1.96× 延迟换 +17.3% 推理质量): 我们要做的是"让下游 agent 好写查询", 不是变成 agent 框架。

## 6. 复现

```bash
# 1) 提取: 用 wal-rust 自己把 600 个候选信号的变更列落成 `.fcol`(见下面的会话命令)
#    600 个候选 = 4 个模式(clk/u_rvsys/cnt/_o)各 150 个, 变更数分布: 0 变更 248 个 / 1-9: 157 / 10-999: 26 / 1k-99k: 22 / >=100k: 147
# 2) 对照:
D=$(ls -d .wal-rust-cache/*-v1.fcol | head -1)
python3 scripts/bench_bttf_sqlite.py "$D" .tools/bttf/slice.txt .tools/bttf/db
# 3) 我们侧的同批查询(单会话):
#    (count (changes "sig")) × 600  →  墙钟 8.32s(含加载, 暖 .fcol)
```

* 脚本只依赖 Python 标准库(`sqlite3`), 不做任何 NPI 调用;`.tools/` 是本地产物, 不入库。
* 本实验**不新增 `bench/perf-history.csv` 行**: 它是"选型对照", 不是我们自己的性能路径;
  等上面第 1/3 条落地后再按版本记行。
